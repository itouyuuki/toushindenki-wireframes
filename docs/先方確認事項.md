#### 実装の重さ

WordPress の仕組み上の事実。※速度の実数は `検証項目.md` で実測して埋めること。

| | 完全一致 | 前方一致・部分一致 |
|---|---|---|
| **案A：型番をタクソノミーに** | **軽い。** ほぼ標準機能。ターム（型番）を直接引くだけ。件数が増えても速度が落ちない。URL も `/model/tsb-ru5234dc/` で自然 | **中。** ターム検索→該当ターム収集→製品を引く、の2段階になる。ただし**型番の一覧は製品数ぶんしかない小さな表**なので、件数の影響は小さい。標準関数だと部分一致になり遅くなるが、**独自SQLで前方一致にすれば速度は保てる** |
| **案C：カスタムフィールドに** | **中。** 標準の `meta_query` で引ける。ただし型番の列には索引が張れないので、案Aより遅い | **重い。** WordPress の LIKE 検索は自動で前後にワイルドカードが付き、**索引がまったく効かない**。全製品を1件ずつ舐めるので、**件数に比例して遅くなる**。件数が多い本件では厳しい |
| **案B：Google** | 制御できない（Google 任せ） | 同左。**新規追加品がクロールされるまでヒットしない**のが本質的な弱点 |

**まとめ：完全一致だけなら案Aがほぼ標準機能で済み、一番軽い。**
前方一致まで求めると案Aでも独自実装が乗り、案Cは件数的に選べなくなる。

#### ⚠ 落とし穴：「完全一致なら安い」とは言い切れない

**A-2（表記ゆれ）を吸収する仕組みは、完全一致を選んでも別途必要になる。**
ハイフンの有無・大文字小文字・全角半角を吸収しないと、
客が `TSBRU5234` と打った時点で **0件** になる。

0件になれば客は電話してくる。**つまり目的が達成できない。**
吸収するには、検索用に正規化した値を別に持つ実装が要る（工数が乗る）。

→ **A-1 と A-2 はセットで聞く。**「完全一致で安く」を選んでも、
　 正規化を入れなければ実質使い物にならない可能性が高い。

#### 先方への出し方（案）

- **完全一致のみ**：安い・速い。ただし**型番を正確に打てた客しかたどり着けない**。
  打ち間違い・うろ覚えの客は 0 件になり、**結局電話が来る**
- **前方一致（`TSB-` まで打つと候補が出る）**：費用は上がる。
  **うろ覚えでもたどり着けるので、電話を減らす目的に直結する**
- **さらに上：入力中に候補を出す（サジェスト）**。最も電話が減るが工数は最大

**目的から逆算すると前方一致以上が要る、という立て付けで提示するのが筋。**
金額を添えて選んでいただく（A-6）。
