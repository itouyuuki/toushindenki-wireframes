# U-1. 状態が変わったときの同期設計 ★社内相談に持っていく

投稿の公開状態が変わったとき、検索用DBをどう追随させるか。
ズレると「**検索に出るのに開くと404**」「**非公開のはずの製品が検索に出る**」が起きる。

## 方針：レコードは消さず `status` で制御する

ゴミ箱から復元される可能性があるため、**物理削除は「完全削除」のときだけ**。
検索時に `WHERE status = 'publish'` で除外すれば足りる。

| WordPress 側の操作 | 検索用DB |
|---|---|
| 公開 | 登録／更新（`status = publish`） |
| 下書き・非公開に変更 | `status` を更新。**レコードは残す** |
| ゴミ箱に入れる | `status = trash`。検索結果から外れる |
| ゴミ箱から復元 | `status` が戻り、検索結果に復活 |
| 完全削除 | **物理削除** |
| 予約投稿 | 公開時刻に自動で `publish` になるので、その時点で登録される |

## 使うフック

| 用途 | フック | 理由 |
|---|---|---|
| **状態遷移** | `transition_post_status` | 公開・下書き・非公開・ゴミ箱・復元を**1つで全部拾える**。個別フックを並べる必要がない |
| **内容の更新** | `wp_after_insert_post` | ★`save_post` を使わないこと（下記） |
| **完全削除** | `before_delete_post` | 物理削除する |

### ⚠ `save_post` ではなく `wp_after_insert_post` を使う

**`save_post` の時点では、カテゴリーや特徴タクソノミーがまだ保存されていない場合がある。**
特徴を検索用DBに複製する設計なので、`save_post` だと**空のまま同期される事故**が起きる。
`wp_after_insert_post` はターム確定後に走る。

### 除外するもの

**リビジョンと自動保存では走らせない。** 放置すると1回の保存で何度も同期処理が動く。

## ⚠ 標準投稿タイプを選んだことの副作用

**製品もお知らせも同じ `post` なので、フックの中で「これは製品か」を自分で判定する必要がある。**
カスタム投稿タイプなら投稿タイプ名で一発だったが、その手が使えない。

**判定は「製品カテゴリー7項目のいずれかが付いている」＋「型番が入っている」の併用を推奨。**
片方だけだと穴が残る：

- カテゴリーだけ → お知らせに誤って製品カテゴリーを付けると検索に出る
- 型番だけ → 型番を入れ忘れた製品が永久に検索に出ない

> 社内で決めること：判定方法をこれでよいか

## 失敗したときの扱い

WP 側と検索用DBは**トランザクションを跨げない**ので、
**投稿は保存できたのに検索用DBへの書き込みが失敗する**ケースが必ず起きる。

→ 投稿保存自体は成功させ、**ログを残す**。回収は U-4 の全件再構築バッチで行う。

> 社内で決めること：ログの出し先と、管理者が気づく手段

# 管理画面まわりに作るもの

**新しい管理画面は作らない。WordPress の管理画面をそのまま使う。**
製品の登録＝投稿の編集画面、カテゴリー＝標準のカテゴリー欄、
特徴＝カスタムタクソノミーを新設すれば自動でチェックボックス欄が出る。

**ただし以下3つは足す。** いずれもテーマ側（`functions.php` / `inc/`）の数十行。

- [ ] **① 型番の専用入力欄（メタボックス）**
      標準のカスタムフィールド欄は「キーと値を手打ち」で、キー名を打ち間違えると黙って動かない。
      数百件を先方が登録するので事故になる。**「型番」ラベルの入力欄を1つ出す。**
      ※ 型番の入力自体は不要にならない（先方しか持っていないデータ）。
      　 **正規化型番（`TS0182BK`）は保存フックが自動生成するので入力不要。**

- [ ] **② 入力漏れの警告**
      カテゴリーか型番が空のまま公開されると検索に出ないが、**先方は気づけない**。
      公開時にチェックして警告を出す。

- [ ] **④ カテゴリー編集画面に「カテゴリー写真」と「並び順」の欄**
      WordPress のカテゴリーが標準で持てるのは**名前・スラッグ・親・説明だけ**。
      製品情報ページのカテゴリー一覧カードに出す**写真**と、
      ヘッダー／フッター／一覧で共通に使う**並び順**は標準では持てない。
      → **タームメタ**で持たせる。画像は添付IDを保存する。
      **プラグインは使わない**（E-1 の対象を増やさないため）。
      **並び順を入れないと名前順／ID順になり、全ページで意図した順序が崩れる。**

- [ ] **③ 検索DBの状態を見る管理ページ（1画面）＋「全件再構築」ボタン**
      検索DBは WordPress の管理画面から見えないので、ズレても先方が気づけない。
      「登録件数 ○件／最終同期 ○月○日」を表示し、**再構築をボタンで実行できるようにする**。
      **先方が自力で登録する以上、コマンドラインを叩かせるのは無理。**
      CSV 一括投入（B-6）の場合も、投入後にこのボタンを押すだけで済む。
      → U-4 の全件再構築バッチはこの形で実装する

## ① 資料・アクセサリーの紐づけ ─ 実装案

8/5 決定「対応アクセサリーは入れる」を満たす必要がある。
型番タクソノミー案が失効したので代替が要る。**アクセサリーも製品カテゴリー7項目の1つ**
なので、実体は「製品の投稿 ⇔ 製品の投稿」の紐づけになる点に注意。

### 案1：検索用DBに紐づけテーブルも持つ ★★ 2026-08-18 これに決定

すでに別DB＋フック同期の仕組みを作るので、**同じ仕組みに相乗りできる**のが強み。

```
search_index          … 型番から引くための表
  post_id / model_raw / model_norm / kind(製品|資料|アクセサリー) / status …

relation              … 何が何に対応するか
  post_id  … 製品の投稿ID
  rel_post_id … 対応する資料・アクセサリーの投稿ID
  rel_type … 'document' | 'accessory'
```

- **入力方法**：資料やアクセサリーの投稿に「対応型番」をテキストで入れてもらう
  （カンマ区切りなど）。保存フックがそれを正規化して `relation` に展開する
- **利点**：検索と紐づけが同じデータソースになり整合しやすい。
  製品詳細の「この製品の資料」「対応アクセサリー」を1クエリで引ける
- **欠点**：WordPress の管理画面から紐づけ状況が見えない。
  貼り忘れ・打ち間違いに気づけないので、**管理画面に確認用の表示を作る**か、
  不整合を検出する仕組みが要る

### 案2：カスタムフィールドに対応型番を持つ

資料・アクセサリーの投稿に「対応型番」カスタムフィールドを持たせ、
製品詳細では `meta_query` の LIKE で引く。

- **利点**：実装が最も軽い。WordPress の管理画面で値が見える
- **欠点**：**`meta_query` の LIKE は索引が効かない**（型番検索を別DBに逃がした理由と同じ問題）。
  製品詳細を開くたびにこのクエリが走るので、件数が増えると詳細ページ全体が重くなる

### 案3：粒度の粗いタクソノミーを使う

型番そのものではなく「**製品シリーズ**」単位のタクソノミーにする。
ターム数が数十〜百程度に収まるならターム爆発は起きない。

- **利点**：WordPress 標準の仕組みで完結。管理画面で見える・選べる
- **欠点**：**アクセサリーの対応関係がシリーズ単位でよいか**は先方確認が必要（C-3）。
  型番単位の対応が必要ならこの案は使えない

### 判断に必要なこと

- [ ] アクセサリーの対応関係は**型番単位か、シリーズ単位か**（→ 先方 C-3）
- [ ] 紐づけデータの元ネタが**どんな形で存在するか**（→ 先方 C-3・B-1）

## ⑤ 検索用DBに何を持たせるか

**原則：持たせるほど「WordPress を引き直さずに検索結果を描画できる」＝速い。
　　　　ただし複製したデータは陳腐化する。**

| カラム | 何ができるようになる | 陳腐化 |
|---|---|---|
| `post_id` | **必須。** WordPress の投稿に戻れる。パーマリンク取得 | しない |
| `model_norm`（`TS0182BK`） | **必須。** 検索対象。ここに中間一致をかける | ー |
| `model_raw`（`TS-0182-BK`） | 検索結果に**整形された型番**を出せる | 型番変更時 |
| `status`（公開状態） | **下書き・非公開を検索から外せる**（U-1 の解決策） | 状態変更時 |
| `kind`（製品/資料/アクセサリー） | **①の串刺しがここで効く。** 同じ型番で種別違いを引ける | しない |
| `title`（品名） | 検索結果一覧を**WordPress に触らず描画できる**＝速い | 品名変更時 |
| `category` | 検索結果を**カテゴリーで絞り込み・グループ表示**できる | 変更時 |
| `thumbnail_url` | サムネイル表示。ただし**メディア差し替えで URL が変わる**ので陳腐化しやすい。`post_id` から都度取るほうが安全 | しやすい |
| `permalink` | リンク生成。**スラッグ変更で陳腐化**。`post_id` から都度生成が安全 | しやすい |
| `updated_at` | **同期ズレの検出**、再構築バッチの差分実行 | ー |

### 【2026-08-18 確定】表示項目は `products.html` の製品カード

**先方承認済みのワイヤー `products.html`（セクション5・製品一覧）と同じ。**
検索結果もこのカードを使い回す。

```html
<div class="pcard">
  <div class="ph">製品写真</div>                 ← ① サムネイル
  <div class="body">
    <span class="cat">IPカメラシステム</span>     ← ② カテゴリー
    <div class="nm">4MP 電動ズーム バレット型 IPカメラ</div>  ← ③ 商品名
    <div class="cd">TSD-IPB2813AF</div>          ← ④ 型番
    <div class="icons"><b>4MP</b><b>PoE</b><b>AI</b>…</div>   ← ⑤ 特徴（複数・可変個）
  </div>
</div>
```

### 確定スキーマ（案）

```
search_index
  id
  post_id        … WordPress の投稿ID。ここから戻る
  kind           … 製品 / 資料 / アクセサリー
  model_raw      … TSD-IPB2813AF（表示用）
  model_norm     … TSDIPB2813AF（検索用・中間一致をかける対象）
  title          … 商品名
  cat_id         … 製品カテゴリー（7項目）の term_id ※階層なしのフラット構造
  cat_name       … 表示用の名前
  features       … "4MP,PoE,AI,WDR,夜間監視,防塵防水"（カンマ区切り・表示用）
  thumb_id       … サムネイルの添付ID（★URL ではなく ID）
  status         … publish / draft / private（U-1 の対応）
  updated_at     … 同期ズレの検出・差分再構築用
```

**設計の理由**

- **サムネイルは URL でなく添付ID (`thumb_id`) を持つ。** 理由は3つ。
  1. **ドメインが変わっても効く。** 本件は**新規ドメインを契約予定**（現行から移管しない）。
     開発中の URL と本番の URL が違うので、URL を複製していると全件書き換えが要る
  2. **サイズ違いを後から選べる。** 同じ ID から thumbnail / medium / large を取れる。
     URL を持つと1サイズに固定され、デザイン変更のたびに作り直しになる
  3. サムネイル再生成や https 化で URL が変わっても追従できる

  ※ **「アイキャッチを差し替えても ID なら安全」は誤り。**
  　 別画像に差し替えると新しい添付になるので ID も変わる。
  　 どちらにせよ保存フックでの更新が必要。
- **`features` はカンマ区切りの文字列で十分。**
  ワイヤーの絞り込み UI は「製品カテゴリー」「中カテゴリー」の2つだけで、
  **特徴での絞り込みはない**（＝表示専用）。絞り込みに使うなら別テーブルが必要になる
- **カテゴリーは term_id と名前の両方を持つ。**
  絞り込みは term_id で行い（名前変更に強い）、表示は名前を使う（WordPress を引かずに済む）

### 特徴（4MP・microSD 等）を WordPress 側でどう登録するか

**【2026-08-18 決定】「特徴」カスタムタクソノミーを新設する。** 種類は数十程度に収まるので、
型番のようなターム爆発は起きない。保存フックで検索DBの `features` に
カンマ区切りで複製する。

※ **企画書で「WordPress はカスタムタクソノミー前提」と明記済み**なので、
　 新設は合意済みの範囲。社長判断の「カスタム投稿タイプを使わない」は
　 **製品を入れる箱**の話であって、分類軸の話ではないため抵触しない。

**対抗案は「標準タグを流用」と「カスタムフィールドに手打ち」。新設が勝る理由：**

1. **表記ゆれが起きない。** チェックボックスから選ぶだけ。
   手打ちだと `4MP` / `4mp` / `4メガ` が混在し、製品カードの見た目がバラつく
2. **名前の一括変更ができる。** `microSD` を `micro SD` に直したいとき、
   ターム名を1回変えれば全製品に反映。手打ちだと全件修正
3. **フックが確実に判別できる。** 「特徴のターム」として取れる。
   タグ流用だと、どのタグが特徴なのかコード側で判別できない
4. **お知らせのタグと混ざらない。** 管理画面のタグ一覧が汚れない
5. **将来「特徴で絞り込み」に拡張できる。** 現ワイヤーに絞り込みはないが、
   後から要望が来ても土台がある（手打ちだと作り直し）

※ 特徴の**表示順**は標準では名前順／ID順。任意の順序にするなら追加実装が要る。

## ⑥ `%TS%0182%` とは（ワイルドカードの説明）

`%` は SQL の **LIKE 検索で使うワイルドカード**で、「**ここに何が入ってもよい（0文字以上）**」
という意味。

```
LIKE '%TS%0182%'
   → 「どこかに TS があって、そのあとどこかに 0182 がある」ものすべて
```

つまり上長の案は、**入力を区切りごとに分割して間に `%` を挟む**やり方。

| 客の入力 | 作られる条件 | `TS0182BK` にヒットするか |
|---|---|---|
| `TS-0182` | `%TS%0182%` | ○ |
| `TS 0182` | `%TS%0182%` | ○ |
| `TS0182` | `%TS0182%` | ○ |
| `ts-0182` | （小文字化して同上） | ○ |

**利点**：ハイフンの位置や区切り方がバラバラでも拾える。表記ゆれに非常に強い。

### ⚠ 注意点（必ず実装に入れること）

1. **`_` も LIKE のワイルドカード**（任意の1文字）。
   **型番に `_` が含まれていると誤動作する。** `%` `_` は必ずエスケープする
2. **SQL インジェクション対策必須。** 入力をそのまま SQL に入れない。
   プレースホルダ（プリペアドステートメント）を使う
3. **区切りを細かくしすぎると誤ヒットが激増する。**
   `%T%S%0182%` のように1文字ずつ分割すると無関係な製品が大量に出る。
   分割は「記号・空白の位置」に限定する
4. `TS` と `0182` が**離れていてもヒット**する。`TS9999-0182` も出る。
   順序は保たれる（TS が先）が、完全な絞り込みではない
5. **最低文字数の制限**を入れる。`0` 1文字で検索されると全件返る

## ⑦ 並び順 ─ 前方一致を上に出す【2026-08-18 採用決定】

**まったく大変ではない。SQL の `ORDER BY` に数行足すだけ。**

優先順位は **完全一致 → 前方一致 → 中間一致**、同順位内は**型番が短い順**。

```sql
ORDER BY
  CASE
    WHEN model_norm = :q            THEN 0   -- 完全一致
    WHEN model_norm LIKE :q_prefix  THEN 1   -- 前方一致（'TS0182%'）
    ELSE                                 2   -- 中間一致
  END,
  CHAR_LENGTH(model_norm),   -- 型番が短いものを先に
  model_norm
```

### 中間一致で完全一致が出てきたときの挙動

**中間一致は完全一致を含む。** `LIKE '%TS0182BK%'` は `TS0182BK` そのものにもマッチするので、
**完全一致の製品は必ず結果に入る。**

ただし**そのままでは順序が保証されない**ので、上の `ORDER BY` がないと
完全一致が3ページ目に埋もれることが起こりうる。

### さらに親切な挙動（推奨・実装は軽い）

**完全一致が1件だけヒットしたら、その製品ページに直接飛ばす。**

8/5 の「**このホームページでこの型番で検索してください、と案内したい**」という
先方の要望に一番効く。客は検索結果一覧を見ずに目的のページに着く。

## ⑧ WordPress テーマの中に独自クエリを書く場合

**制限らしい制限はない。テーマ内で問題ない。** むしろ利点が大きい。

### 具体的に何をするのか（ファイル単位の話）

**「WordPress を介さない」と「テーマ内に書く」は矛盾しない。**
- 「WordPress を介さない」＝ 検索の**クエリ**を `WP_Query` に頼らず、自分で SQL を書く
- 「テーマ内に書く」＝ その**置き場所**が WordPress のテーマフォルダの中

つまり **WordPress のサイトの一部として、検索ページを1枚自作する**ということ。

```
wp-content/themes/<テーマ名>/
├ header.php                  … 既存（そのまま使う）
├ footer.php                  … 既存（そのまま使う）
├ page.php                    … 既存。通常の固定ページ
├ page-product-search.php     ★新規。型番検索ページの中身
├ functions.php               … 既存。ここから下を読み込む
└ inc/
   ├ search-index.php         ★新規。保存フックで検索DBへ登録する処理
   └ search-db.php            ★新規。検索DBへの接続と検索の関数
```

**手順**
1. WordPress の管理画面で固定ページ「型番検索」を作る
2. そのページのテンプレートに `page-product-search.php` を割り当てる
3. `page-product-search.php` の中身は、おおよそこの流れ

```php
get_header();                          // 既存のヘッダーをそのまま使う

$q = $_GET['model'] ?? '';             // ?model=TS-0182 を受け取る
```

### 注意点

1. **別DBの接続情報は `wp-config.php` に定数で置く。**
   テーマ内にベタ書きしない（テーマ更新で消える／Git に載る）
2. **接続は検索ページでのみ張る。** 全ページで張ると無駄
3. **プリペアドステートメント必須**（⑥の注意2と同じ）
4. **キャッシュプラグインとの相性。** 検索結果ページがキャッシュされると
   古い結果が出る。除外設定が要る
5. **テーマを差し替えると独自コードが消える。**
   将来性を取るならプラグイン化する手もあるが、
