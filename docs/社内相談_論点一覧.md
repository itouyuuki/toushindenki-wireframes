### 2. トピックス（新製品バナー）の表示 ✅
**8/17 の論点**：最大3枠。件数が少ないときの並び。**スマホでの並べ方**
（縦に積むか、バナー左・タイトル右の横並びにするか。技術顧問は後者を提案）。

**実装方針**：
- 「新製品」タグが付いた製品投稿を**投稿日の新しい順に3件**拾って表示
- 0〜2件のときは中央寄せ
- **リンク先はその製品の個別ページ**（論点3の帰結。製品投稿から拾うので自然にそうなる）
- PC は3枠横並び（現ワイヤーどおり）。**スマホはバナー左・タイトル右の横並び**

**タグの削除運用は不要。** 最新3件で取るので、古いタグは付けっぱなしでよい。
4件目以降は自動で表示から外れる。**運用を強制しない形にしておく**。

⚠ **ただし枠が余ると前回分が残る。** 例：8月に3件登録 → 翌2月に2件登録すると、
最新3件＝新しい2件＋8月の1件。実害は小さいので、気になったときだけタグを外してもらう。

バナー画像の持たせ方は**論点23**に分離（8/18 に決着）。

※ **リンク先が製品個別ページであることはワイヤーに明記されていない**（注釈は 8/5 に全削除済み）。
　 設計上そうなるというだけなので、色分けのときに明示する。

## 製品情報

### 4. 型番検索の実装方法 ✅【8/18 に確定】
**8/17 の論点**：3案（型番タクソノミー／Google サイト内検索／カスタムフィールド）とも一長一短。
カスタムフィールドは「件数が多いとお話にならない」、タイトルは完全一致のみ、日本語全文検索は不確か。

**実装方針**：**WordPress を介さず PHP で独自構築する。**
1. 製品保存時にフックで型番を正規化（`TS-0182-BK` → `TS0182BK`）
2. **検索用の別DB**に登録（WP用と検索用の2DB構成）
3. 検索は **`%TS%0182%` 形式の中間一致**
4. 並び順は**完全一致 → 前方一致 → 中間一致**、同順位は型番が短い順
5. 検索ページはテーマ内に `page-product-search.php` を新規作成（固定ページに割り当て）

**なぜ**：`products.html` のヒント文「型番の一部だけでも検索できます。大文字・小文字、
ハイフンの有無は問いません」が**先方承認済みの約束**。これを満たす必要がある。

### 5. 型番を何で持つか ✅【8/18 に確定】
**8/17 の論点**：カスタムフィールドは検索できない。タクソノミーならターム数が爆発する。
**実装方針**：**カスタムフィールドで持つ**（表示用）。**検索は別DBの正規化済みの値で行う**。
タクソノミーにはしない。

### 6. 製品は投稿かカスタム投稿タイプか ✅【8/18 社長判断】
**8/17 の論点**：標準カテゴリーだと製品のカテゴリーがお知らせと同じ一覧に並び、視認性が壊れる。
**実装方針**：**標準の「投稿」タイプを使う。**
型番をタクソノミーにしないので、ターム爆発の問題自体が起きない。

**副作用**：製品もお知らせも同じ `post` になるので、
フックの中で「これは製品か」を自分で判定する必要がある。
→ **親カテゴリー「製品」の配下かどうかで判定する**（論点7・13）。8/18 に解決済み。

### 7. カテゴリーの階層 ✅【8/18 更新】
**8/17 の論点**：カテゴリーは親子あり、タグは親子なし。どちらで持つか。
**実装方針**：**「製品」という親カテゴリーを1つ新設し、その下に7項目をぶら下げる。**

```
カテゴリー
├ 製品              ← ★新設。論点13の判定に使う
│  ├ IPカメラシステム
│  ├ Wi-Fiカメラシステム
│  ├ ソーラーバッテリーカメラ
│  ├ SIMカメラシステム
│  ├ AHDカメラシステム
│  ├ イージーシリーズ
│  └ アクセサリー
└ お知らせ
   ├ ファームウェア更新
   └ 長期休暇 …
```

**7項目の下に中カテゴリーは作らない**（8/18 に不要と判断し `products.html` から削除済み）。
**7項目の上に親を1つ置くのは別の話**なので矛盾しない。

**おまけ**：管理画面のカテゴリー一覧が「製品」と「お知らせ」の2グループに分かれるので、
論点6で懸念した「製品とお知らせが混ざって見づらい」問題も緩和される。

### 8. 製品の「特徴」表示（4MP・microSD 等） ✅
**8/17 の論点**：正方形アイコンに揃えると文字数で折り返しが破綻する（「夜間監視」は収まるが
「夜間稼働あり」で崩れる）。画像で作ると WordPress の管理外になる。
**実装方針**：
- 見た目は**幅可変のテキストラベル**（正方形をやめる）
- データは**「特徴」カスタムタクソノミーを新設**してチェックボックスで選ばせる
- 保存フックで検索用DBに `"4MP,PoE,AI,…"` とカンマ区切りで複製（表示専用）

**なぜタクソノミー**：手打ちだと `4MP`/`4mp`/`4メガ` が混ざる。
チェックボックスなら表記ゆれが起きず、名前の一括変更もできる。

## ダウンロード

### 11. カタログ差し替えで URL が変わる問題 ✅【8/18 に解決】
**8/17 の論点**：メディアに新ファイルを上げると別 URL になる。
旧 URL をブックマークされていると古い版を指したまま。

**実装方針**：2段構えにする。**どちらも軽いので分けて見積もる意味はない。**

1. **ダウンロードボタンを動的生成する**（コストほぼゼロ）
   PHP がページ表示のたびに「この資料の今の添付ファイル」を読むので、
   **差し替えた瞬間にボタンの行き先も切り替わる。人手の張り替えはゼロ。**
   8/17 の懸念が当てはまるのは**URL が固定で書かれている場合**（本文に手で貼った等）で、
   動的生成なら起きない
2. **固定 URL を1枚かませる**（数十行）
   `/download/?doc=総合カタログ` のような**変わらない URL** を客に持たせ、
   中で今の添付ファイルへ転送する。**客がブックマークしても生き続ける**

**メディア本体にカスタムフィールドやタクソノミーを付ける必要はない。**
資料は投稿として登録し、対応型番はその投稿に持たせるため（論点9・12）。
→ 8/17 に「要調査」としていたメディアのカスタムフィールドは**調査自体が不要になった**

⚠ **残る運用リスク**（技術で防げないので先方に伝える）
- 差し替えは「**投稿の添付を差し替える**」で行ってもらう。
  新しいメディアを追加してリンクを張り直されると URL が変わる → C-1
- **先方が客にファイル URL を直接メールで送っている場合**は差し替えで死ぬ → C-2

## 同期・管理画面（8/18 に新しく出た論点）

### 13. 「これは製品か」の判定 ✅【8/18 に決定】
**論点**：論点6の副作用。製品もお知らせも `post` なので、フック内で判定が要る。
**実装方針**：**親カテゴリー「製品」の配下かどうかで判定する。これだけ。**

**なぜ7項目のIDを列挙しないか**：8個目のカテゴリーが追加されたとき、
**列挙方式だとフックのコードを直さないとその製品が検索に出ない**。
先方は管理画面からカテゴリーを追加できるので、これは実際に起きる
（現行サイトは8項目だったので増える可能性は十分ある）。
**親で判定すれば、先方が「製品」の下に足すだけで自動的に対象になる。**

**型番の有無は判定条件に入れない。**
入れると、型番を入れ忘れた製品が検索用DBに一切載らず、後から型番を入れても復旧経路が要る。
型番が空の製品もカテゴリー一覧や TOPICS には出したい。
→ **型番の入れ忘れは「入力漏れの警告」で拾う**（論点16の②）。役割を分けるとどちらも単純になる。

### 14. 状態が変わったときの同期 ⚠★
**論点**：公開・下書き・非公開・ゴミ箱・復元・完全削除で、検索用DBをどう追随させるか。
ズレると「検索に出るのに開くと404」「非公開のはずの製品が検索に出る」。
**`status` とは**：WordPress に最初からある**投稿ステータス**（`publish` 公開済み／
`draft` 下書き／`pending` レビュー待ち／`private` 非公開／`future` 予約投稿／`trash` ゴミ箱）。
投稿一覧の上のタブがこれ。**検索用DBに持つ `status` は、WordPress 側の値の写し。**
**別DBなので JOIN できず**、持っていないと検索結果1件ごとに WordPress へ
「まだ公開中か」を問い合わせることになるため。

**実装方針（案）**：
- **レコードは消さず `status` で制御**（ゴミ箱から復元されうるため）。完全削除のときだけ物理削除
- **検索に出すのは `publish` のみ。`pending`（レビュー待ち）は必ず外す** ★
  企画書の運用が「**公開権限あり／なしの2種アカウント。複数人編集＋管理者が公開判断**」なので、
  **編集者が登録 → `pending` → 管理者が承認 → `publish`** という流れが実際に走る。
  **レビュー待ちが検索に出ると、承認前の情報が客に見える。**
  `transition_post_status` で拾えるが、仕様に明記しないと実装時に漏れる
- 状態遷移は **`transition_post_status` で一括で拾う**（公開・下書き・ゴミ箱・復元を1つでカバー）
- 内容更新は **`save_post` ではなく `wp_after_insert_post`**
  （`save_post` の時点ではタームが未保存で、**特徴が空のまま同期される事故**が起きる）
- 完全削除は `before_delete_post`
- **リビジョンと自動保存では走らせない**

⚠ **相談したい**：この設計で拾えない経路があるか。

### 15. 同期に失敗したとき ⚠
**論点**：WP と検索用DBは**トランザクションを跨げない**。
投稿は保存できたのに検索用DBへの書き込みが失敗するケースが必ず起きる。
**実装方針（案）**：投稿保存自体は成功させ、ログを残す。回収は論点16の再構築ボタン。

⚠ **相談したい**：ログの出し先と、先方が異常に気づく手段。

### 16. 管理画面に足すもの ✅
**論点**：初期登録は**先方が実施**と決まった（数百件）。管理画面の使い勝手が成否を分ける。
**実装方針**：**新しい管理画面は作らない。WordPress の管理画面をそのまま使う。**
ただしテーマ側に3つ足す。
1. **型番の専用入力欄（メタボックス）** — 標準のカスタムフィールド欄は
   「キーと値を手打ち」で、キー名を間違えると黙って動かない
2. **入力漏れの警告** — カテゴリーか型番が空のまま公開されると検索に出ないが先方は気づけない
3. **検索DBの状態表示＋「全件再構築」ボタン**（1画面） —
   **先方にコマンドラインは叩かせられない**

🔍 **未確認**：先方が**どうやって登録するか**（1件ずつ手作業か、CSV 一括投入か）→ 先方 B-6。
一括投入だとフックが走らず、検索用DBが空のままになる。

## 画像（8/18 に追加した論点）

### 23. 製品写真とバナーの持たせ方 ✅【8/18 に決定】
**論点**：製品詳細の FV は**製品の全体像の写真**にしたい。
TOPICS のバナーは**文字が焼き込まれたデザイン画像**で別物。
**1投稿にアイキャッチは1枚しか持てない**ので、どう分けるか。

**実装方針**：役割で2つに分ける。**どちらもお客様が登録できる。**

| 画像 | 用途 | 持たせ方 |
|---|---|---|
| **製品写真（全体像）** | 製品詳細の FV／一覧カードのサムネイル／検索結果のサムネイル | **アイキャッチ画像**（標準機能） |
| **TOPICS バナー** | 新製品としてトップに出すとき | **追加の画像フィールド**（メタボックス） |

追加フィールドは**メディアライブラリから選ぶボタン**を出すので、操作はアイキャッチとほぼ同じ。
仕組みは**型番のメタボックスと同じ**で、中身が文字か画像かの違いだけ。

**バナーは未登録でも壊れない形にする。**
必要なのは新製品タグを付けた3件だけなので、全製品に登録させるのは無駄だし忘れられる。
**バナーが空ならアイキャッチ（製品写真）で代替する。**

**製品写真は1枚だけ**で確定（複数枚のギャラリーは作らない）。
→ ワイヤーの「製品写真（メイン）」という表記は
　 「サブ写真もある」と読まれかねないので**「製品写真」に修正済み**。

# 聞き方

**「できますか？」と聞かない。**「できます」で終わって知見が出ない。

8/17 で価値があったのは、技術顧問が**自分から危険を挙げた**ところだった
（「さっと追加しちゃうところが実は怖い」「使い慣れてるっていうことはあって、危険だよ」）。

| ✕ | ○ |
|---|---|
| この設計でできますか？ | **この設計、どこが危ないですか？** |
